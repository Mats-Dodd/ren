<H n="1.2.3">Reading the signature</H>

<Aside>Pins are numbered counter-clockwise from the notch, as on a real part. Inputs enter on the left; results and faults leave on the right.</Aside>

`main` writes nothing about what it touches, yet it touches the terminal. A private function's dependencies and errors are inferred; a `pub` one writes them out in full. Either way the compiler knows them, and the manual draws them as a pinout. Effects show as lamps along the base: <LampPanel on={['IO']} />

<Pinout sig={main} fig="1-1" caption="main takes nothing, uses Console, returns Unit and cannot fail. The uses pin was inferred from the call to print." />

<Callout>
  <span>`uses` is not an import. A dependency is installed by whoever runs the code. In a test, `Console` is a test implementation that records what was written; under `ren run`, it is the terminal.</span>
</Callout>

Every call that can fail is marked. An unmarked one is an error, so the places a function can stop are visible when you skim it.

`try` moved the error up one level, so `main` can fail too. Ask the compiler what it inferred:

<Listing n="1-6" title="Inferred signatures" lang="shell" code={types} />

<Pinout sig={checkSig} fig="1-2" caption="check: one input, one result, one fault output. The FAIL lamp is lit." />

Change the call to `check(-1)` and run it again. `main` fails, so the program prints the error and exits with status 1:

<Listing n="1-7" title="main fails" lang="shell" code={"$ ren run check.ren\nerror: Negative(-1)"} faultLines={[2]} />

<Callout kind="design">
  <span>Why can't a call that might fail go unmarked? Because the signature is the contract and the body is read quickly. A reviewer skimming `main` should see every place it can stop without opening `check`. The marker costs four characters; a hidden exit costs an incident.</span>
</Callout>
