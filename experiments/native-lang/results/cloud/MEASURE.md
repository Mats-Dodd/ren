# Phase B Measure: C vs Rust vs Zig, machine "cloud"

**Machine: cloud.** The spec is in `experiments/MACHINE-cloud.md`: 4 vCPU Xeon under KVM (the guest is Firecracker), Linux 6.18, with io_uring available.
- Date: 2026-10-30. Measuring ran from 17:06 to 20:00 UTC.
- Toolchains: clang 18.1.3, clang-22/lld-22 (for cross-language LTO), tcc 0.9.27+git20200814, rustc 1.97 stable, zig 0.17.0, liburing 2.5, qemu-aarch64-static 8.2.2 and wasmtime 25.0.3.
- Everything was measured strictly serially, one configuration at a time.

## 0. Method

**Locks**
- Every timed configuration ran under `flock -x /tmp/ren-bench/lock`, held for all of that configuration's repetitions.
- Every untimed step ran under `flock -s`: builds, tests, cross builds, probes and qemu runs.
- So no two timed configurations ever overlapped, and no build or test overlapped a timed run.

**Driver script:** `harness/measure_b.py` (new; `measure.py` is unchanged). It follows the task's rule:
- 10 repetitions per configuration. W2 at 4 and 8 workers uses 7, because each run takes 18 to 34 s. Build timing also uses 7.
- It records median, min and max, and `/proc/loadavg` at the start and end of every attempt.
- **spread = (max − min) / median.** If the spread of *any* headline metric of a configuration is over 10%, the configuration is re-run, up to 2 more times. If it is still over 10%, it is marked **NOISY** and is never used as a headline.
- Every attempt is kept in the `.jsonl` record.

**Data and table generation**
- The raw data is in `results/cloud/*.jsonl`. Each object carries `"machine": "cloud"`, the exact `cmd`, every sample and every attempt.
- The tables below are generated by `python3 -I harness/measure_report.py`.
- The job scripts that ran everything are kept as `results/cloud/measure-job{A..E}.sh`. They refer to the scratchpad paths they were run from.

**Load:** the 1-minute loadavg at the start of a configuration includes the *previous* configuration's own threads. Nothing else ran on the box during the timed runs (checked with `ps`).
- At 1 worker it sits around 1.0 to 1.7.
- After the 4- and 8-worker runs it is 2 to 4.5.
- Steal time sampled during a 1-worker run was about 3.4% of one vCPU.

**Noise is the main limitation of this machine.** Runs at 1 worker take 0.1 to 0.7 s and vary 15 to 50% run to run on this VM.
- That held even pinned with `taskset -c 1` (jobC and jobE) and at 10× the W1 size.
- So most 1-worker W1/W2/W4/W5 configurations are NOISY, and there is no all-three-languages headline for them.
- The multi-worker configurations run for seconds and are stable, at 2 to 9% spread.

**Language builds measured (release form):**

|---|---|
| `c-release` | clang -O2 |
| `rust-release` | std, panic=abort, stable |
| `rust-release-nostd` | no_std + alloc |

## 1. Clean rebuild and W1-W4 re-check

At 17:06 UTC every release build and target directory was deleted, along with `zig/.zig-cache`. Then each build was rebuilt with `./build.sh c release`, `./build.sh rust release`, `./build.sh rust release-nostd` and `./build.sh zig release-fast`.

The suites were then run as:

```
WORKERS="1 4 8" DRIVERS="epoll uring" harness/test.sh bin/<tag> layout abi deque smoke io replay
```

| build | result |
|---|---|
| c-release | 71/71 |
| rust-release | 71/71 |
| zig-release-fast | 71/71 |
| rust-release-nostd | 70/71 (`t_timer uring x4` failed once, see below) |

The suites cover:
- layout, abi_test, and deque empty/lifo/stress;
- W1-W3 at 1, 4 and 8 workers on both drivers;
- t_timer, t_pipe, t_tcp, t_cancel and t_block stop/kill;
- W4 record and replay of w1, w3, t_cancel and t_timer on both drivers, plus the flipped-byte and truncated-journal refusals.

Log: `results/cloud/measure-functional.txt`.

**t_timer is flaky in every core: a harness-test limitation, not a core bug.** I ran 100 runs per (core, driver, workers) for 24 configurations (`harness t_timer`). It failed in 10 of the 2,400 runs.

| core | epoll x1 | epoll x4 | epoll x8 | uring x1 | uring x4 | uring x8 |
|---|---|---|---|---|---|---|
| C | 0 | 2 | 0 | 0 | 0 | 0 |
| Rust std | 0 | 0 | 1 | 0 | 0 | 2 |
| Rust no_std | 0 | 0 | 0 | 1 | 0 | 1 |
| Zig | 1 | 0 | 0 | 1 | 0 | 0 |

- It happens at 1 worker too, on both drivers, and in all four cores.
- The five sleeps are only 5 ms apart, and the finish order is taken after a second (MONO_NOW) world call. A host stall over 5 ms delivers two expiries in one poll, and they then run in deque (LIFO) order.
- The deadline window check (≤ +200 ms) never failed. Only the order check did.

**W4 byte-match, cross-language** (`results/cloud/measure-w4-xreplay.txt`):
- The timed journals are W1 with n=1M (220,606 B, 7,877 entries) and W3 with n=200k (152,401,330 B, 2,400,023 entries). They were recorded at 1 worker by each core on each driver: 12 journals.
- Every journal replayed in every core: **36/36 output-identical, and every core entry matched byte for byte.**
- The journal files themselves are byte-identical (md5) across C, Rust and Zig for W1, and between C and Zig for W3.
- Rust's W3 journals differ only in *driver* entries. Rust's drivers write `REPLY` before `DRAINED` when a call completes synchronously during the drain, where C and Zig write `DRAINED` first. Core entries are identical, so cross-replay still matches. This is a driver-loop-shape difference from SPEC §C.1, not a core divergence.

**The Zig aarch64 deque failure is a qemu artifact, not evidence of a Zig bug.**
- On aarch64, Zig's fence-free substitution (SPEC §A.3: SC store, then SC load) compiles to `stlr` then `ldar`, which ARMv8 orders (RCsc). C and Rust use `fence(SC)` and emit `dmb ish`.
- A store-buffering litmus (`results/cloud/measure-qemu-sb-litmus.c`, built by zig cc for aarch64) produced **8,815 forbidden outcomes out of 2,000,000 under qemu with `stlr`/`ldar`**, and 0 with relaxed ops plus `fence(SC)`. So qemu-user 8.2 on an x86 host does not order STLR→LDAR, and C code written with seq_cst stores and loads would fail the same way.
- Real aarch64 hardware was not available, so the Zig deque on aarch64 is **untested**. qemu cannot validate it.

## 14. Toolchain a user needs for `ren build`, per language

**C**
- Needs a C11 compiler (clang or gcc), plus liburing headers and the library for the io_uring driver.
- Release-debug tcc works on x86-64 with the slice.h shim; the uring driver still needs clang/gcc.
- Cross builds: `zig cc` (bundles musl plus kernel headers), plus liburing built per target, plus an epoll_pwait2 shim for musl.
- No extra runtime libraries.

**Rust**
- rustc and cargo (stable 1.97), plus rustup targets per triple.
- The `libc` crate from crates.io (or vendored).
- At build time: the bindgen CLI 0.66.1 **and libclang 18 specifically**. With libclang-22, which is now on this box, bindgen silently emits opaque structs; build.rs asserts against that.
- Kernel uapi headers (`linux/io_uring.h`).
- Link time: libgcc_s, or libgcc_eh / libunwind for static and musl links, because std and alloc unwind.
- Cross builds also need a target C sysroot's headers for bindgen (`BINDGEN_EXTRA_CLANG_ARGS`).
- Cross-language LTO needs clang-22 and lld-22 matching rustc's LLVM 22.
- TSan needs nightly plus `-Zbuild-std`.
- Disk: about 1.2 GB for the stable toolchain, plus about 1 GB of llvm-18 for libclang.

**Zig**
- zig 0.17.0 exactly, one 411 MB directory, which brings clang 22, musl, wasi-libc and kernel headers.
- Safe builds need `-fcompiler-rt` (`__zig_probe_stack`).
- Nothing else for build or cross builds.
- A host C compiler still compiles the harness or emitted C, and `zig cc` can be that compiler.

## 15. What this says about SYNTHESIS §4's criteria (measurement-only items)

**Rust takes layer C**
- "W1-W3 within 10% of C": **met** on every clean (multi-worker) row; Rust is often faster.
- "unsafe under about a third": **not met** (66.8%).
- "tcc on Linux links the Rust staticlib": **only no_std**, with `libgcc_eh.a` added. **std does not link** (TLSGD).
- "no_std adds under about 100 KB": **met only with `--gc-sections`** (+86 KB). Without it, +311 KB.
- P3-P5 at compile time: not measured here (the plants are a separate step).

**Zig**
- Speed is close to C: W1 x8 −12/−14%, W2 within 7%, W3 better.
- There is no layout-sync burden: translate-c propagated a/b/c and caught d.
- The Zig 1.0 condition stands. The aarch64 qemu result is inconclusive, not negative.

**C's case strengthens if...**
- "tcc compiles and passes the C core": **yes on x86-64 (72/72)**, through the asm shim.
- "E1 shows an opaque runtime costs over 2%": **not shown**. Unity vs split are equal within noise.
- But edit d shows C is the language that misses a type change in slice.h silently.
